Vicello Data Protection Review

Vicello Pricing Platform 0.3.230 October 2026 · Rev 01Prepared from the actual source code and the live Render setup

This review covers how the platform stores data, what could be lost, and the exact changes needed so that no business data is lost.

Today

Every copy of the data lives in one Render account. The database, the 14 automatic backups and Render's 7 daily snapshots all sit on, or next to, the same 1 GB disk. If that disk, that service or that account is lost, every copy goes with it. The only copy that survives is a backup the owner downloads by hand. Up to a full day of work can be lost even when things go well.

After the plan in section 9

Encrypted copies go to a second, unrelated provider every 15 minutes that data changes. They are locked, so nobody can delete them, not even someone with the Render password. Old versions are kept for 7 years. A restore into a brand-new site takes about 30 minutes, the restore is tested automatically every week, and alerts go out if a backup is ever missed. Added running cost: about US$0–3 a month.

1Current architecture review

How it works today

  • One program, one file. It is a Node.js web server with no third-party packages. All business data is held in a single SQLite database file, /var/data/platform.db, which runs in WAL mode with foreign keys enforced.
  • Hosting: one Render web service (Starter plan, Singapore region) with one 1 GB persistent disk at /var/data. The disk can only be attached to one running copy of the program at a time.
  • Code: GitHub repository MichealMammone/vicello-platform, uploaded through the GitHub website. Render deploys every commit automatically. Each release is also saved as a Rev zip in OneDrive.
  • What the database holds: the company and its settings, users (with scrypt password hashes), sign-in sessions, every price book version, jobs, areas and lines, issued quotes, job costs, staff, leave, the calendar and the activity log. Clients' names, emails, phone numbers and site addresses are stored on jobs.
  • Files and documents: there are no uploaded files. A quote is a frozen JSON copy with a SHA-256 hash, stored in the database and drawn as a web page. Restoring the database therefore restores every quote exactly.
  • Backups today: VACUUM INTO makes a clean, consistent copy while the program runs. It makes one automatic copy a day, keeps the last 14 and never deletes manual copies. All of them go to /var/data/backups, on the same disk as the database. Render also snapshots the disk once a day and keeps each snapshot for 7 days.

Today: the database and every automatic copy are inside the same Render account. The only thing outside it is a file someone remembers to download.

Strengths to keep

  • The whole business fits in one small file. That makes backup and restore portable and fast; there's no cluster to rebuild.
  • With no dependencies, the program runs anywhere Node runs: Render, another cloud, or the office PC (Start Pricing Platform.cmd). That makes for an unusually good disaster fallback.
  • Published price books are locked by database triggers. Issued quotes never change and are hashed. Jobs are archived rather than deleted, and users are deactivated rather than deleted.
  • Saves use optimistic locking, so two people can't silently overwrite each other. There is an activity log, and 52 automated tests.

Single points of failure

The single points of failure are: the one Render disk; the one Render account; the one region; the owner's email inbox, which can reset every other account; the one person who knows the restore steps; and GitHub, as the only route code takes to the live site.

3Backup strategy

The plan follows the 3-2-1-1-0 rule: 3 copies of the data, on 2 kinds of storage, 1 of them off-site, 1 of them impossible to delete, and 0 errors when tested.

Why 15 minutes "if changed": the database is under 5 MB, so a copy takes well under a second and costs almost nothing to store. Nothing is uploaded overnight or at weekends when nobody is working. Publishing a price book or issuing a quote also triggers a copy within 2 minutes, so the most important events are protected almost at once.

Storage needed: about 3.5 GB of recent copies, 2 GB of daily copies and 0.4 GB of monthly copies, which is inside Backblaze's 10 GB free allowance (copies compress to about a third of their size).

Chosen combination: keep the built-in copies and Render snapshots for fast, local undo; send encrypted, locked copies to Backblaze B2 every 15 minutes for disaster recovery; keep a quarterly offline copy as the last resort; and use Healthchecks.io and UptimeRobot to report any failure. Each layer covers a different failure, and no single account can delete all of them.

5Disaster recovery plan

Targets after the plan: RPO (the most work that can be lost) of 15 minutes. RTO (time until staff can work again) of 30 minutes on Render, or 1 hour on the office PC.

Database deleted or corrupted RTO 15–30 min

  1. Settings → Backups → pick the last copy marked "Checked ✓" → Restore. A safety copy of the current state is taken first.
  2. If the site won't start, restore the latest Render snapshot (Render → Disks).
  3. If the disk is gone, follow "Render unavailable" below.
Data lost ≤ 15 minLimit: anyone signed in at the time must sign in again

App corrupted or bad deploy RTO 5 min

  1. Render → Events → previous deploy → Rollback.
  2. If the bad version changed the database, restore its automatic pre-upgrade copy.
  3. Fix the code, run the tests, and upload again.
Data lost noneLimit: older versions can't read newer price book fields (see the deployment guide)

GitHub compromised or deleted RTO 1 h

  1. Render → Settings → turn Auto-Deploy off at once.
  2. Check the last deploys for anything you didn't upload. Roll back if needed.
  3. Create a new repository, upload the latest Rev zip from OneDrive, and reconnect Render.
  4. Change the GitHub password and keys, and review who has access.
Data lost noneLimit: the site keeps running while this is done

Render unavailable or account lost RTO 1 h (PC), 2–4 h (new cloud)

  1. Fast fallback: on the office PC, run Restore From Backup.cmd. It downloads the latest copy from B2 and asks for the encryption key. Then double-click Start Pricing Platform.cmd. Staff use it on the office network.
  2. Permanent: create a new service (another Render account, Railway, Fly.io or DigitalOcean) and choose "Restore from backup" on the setup screen.
  3. Point the web address at the new site and tell staff.
Data lost ≤ 15 minLimit: the office-PC fallback only works inside the office until it is moved back to the cloud

Someone deletes or overwrites data RTO 10 min

  1. Find when it happened in Settings → Activity log.
  2. Open the job → History → pick the version before the change → Restore this version (new job revisions).
  3. For older or wider damage: Settings → Backups → Restore one job from a backup. Only that job is copied back.
Data lost noneLimit: archived jobs can already be un-archived today

Render account taken over RTO 1–4 h

  1. Recover the account through Render support, and secure the email inbox first.
  2. Rotate the B2 write key and the setup values. Nothing in B2 can have been deleted.
  3. Restore into a clean service, as in "Render unavailable".
  4. Reset all user passwords. The restore clears every sign-in session.
Data lost ≤ 15 minLimit: anyone in the account could read the live data; report it under the Privacy Act if client data was exposed

6Data restore process

Because quotes, users and price books all live in the one database, restoring one backup file brings back the whole business. That includes user accounts: everyone signs in with their usual password. There are no separate document files to restore today. If photos or plans are uploaded later, they will go to B2 with versioning, and each backup's manifest will list them.

Restore into a fresh deployment (new build)

  1. Create the new service with a disk from the same code, the way the deployment guide does. Or, on a PC, unzip the Rev package.
  2. Open the site. The setup screen offers Set up a new company or Restore from a backup.
  3. Enter the setup key from the logs. Then either choose Latest off-site backup (if the B2 read key is set on this service) or upload a backup file. Then enter the backup encryption key.
  4. The program checks the copy before using it. It decrypts it, compares the SHA-256 checksum with the manifest, and runs PRAGMA integrity_check and foreign_key_check. It confirms the database version is one it can read.
  5. It shows what it found: company name, last activity, and how many jobs, quotes, users and price books there are. You press Restore.
  6. It installs the database, brings it up to date, clears old sign-in sessions, records "restored from backup …" in the activity log and takes a fresh backup straight away.
  7. Sign in, open the latest job, and run Price book → Spreadsheet check (it should show 0 mismatches). Done.

The same check-then-restore runs from Settings → Backups on a live site (owner only, password re-entered, safety copy taken first), and from Restore From Backup.cmd on a PC. The code is the same in all three places, so the steps are tested once and work everywhere.

Building the full enterprise stack now would cost roughly US$150–400 a month and need ongoing specialist care, for little real benefit at Vicello's size. The plan below gets the "never lose data" result at a small fraction of that cost. The code is already built so it can move to PostgreSQL later: every service talks to the database through one small interface.

8Specific recommendations for this codebase

Immediate This week, no code changes

  1. Turn on two-step sign-in (an authenticator app) for GitHub, Render and the email inboxes that can reset them.
  2. Until v0.4.0 is live: once the site is set up, the owner downloads a backup every Friday into a "Vicello Backups" folder in OneDrive.
  3. Render → Account → Notifications: send failed deploys and service events to two people.
  4. Create a free UptimeRobot monitor on https://vicello-platform.onrender.com/api/state every 5 minutes, alerting two people.
  5. Write down who holds which login, and store the logins in a password manager that two trusted people can open.

High Release v0.4.0, Data protection

  1. Off-site backup service: compress, encrypt (AES-256-GCM) and upload to any S3-compatible bucket. Every 15 min when changed, 2 min after a publish or quote, and the daily and monthly tiers. Built with Node's own crypto and zlib, so there are still no dependencies.
  2. Backup manifest + checks: integrity check, foreign-key check, SHA-256, row counts, app and database version on every copy.
  3. Pre-upgrade copy: a backup is taken automatically before any database change runs (database.js).
  4. Restore from backup: on the setup screen, in Settings → Backups, and in Restore From Backup.cmd, as in section 6.
  5. Alerts and status: a Healthchecks.io ping after each good upload. Settings → Backups shows "Last off-site copy 12 min ago ✓", and owners see a red banner if it is more than 2 hours old.
  6. Weekly automated restore test (.github/workflows/restore-test.yml).
  7. DR runbook: a one-page printable version of section 5 with the drill log.

Medium v0.5

  1. Job version history: each save keeps a copy of the job, so any save can be undone, plus restore one job from a backup. This needs one new table, added alongside the existing ones; nothing existing changes.
  2. Records that are now deleted for good (job costs, templates, leave) get a "removed" mark instead, so they can be brought back.
  3. Two-step sign-in (authenticator app codes) for owner and admin accounts.
  4. A GitHub ruleset on main: no deleting the branch, no force-push, and only the named people can commit.
  5. An email to the owner on important events: a price book published, a backup restored, a new owner or admin added, repeated failed sign-ins.

Future scaling When a trigger is met

Triggers: a second company, more than about 30 people using it at once, the database passing 1 GB, file uploads, or a need for zero-downtime deploys.

  1. A PostgreSQL adapter for server/db/database.js, and managed PostgreSQL in Sydney with point-in-time recovery (estimated about 48 hours of work, as in the hosting proposal).
  2. Two or more instances, uploads in object storage, and error tracking.
  3. The off-site backup design stays the same: pg_dump replaces VACUUM INTO.

Configuration steps

Vicello's owner or Scale Point Group does these, because they involve creating accounts and handling keys.

  1. Backblaze account under a Vicello email that is not the Render login. Turn on two-step sign-in.
  2. Bucket vicello-backups-plus a random suffix: private, Object Lock on, default retention Compliance, 30 days.
  3. Lifecycle rules: recent/ deleted after 31 days; daily/ deleted after 400 days; monthly/ kept (each copy is locked for 7 years when uploaded).
  4. Two application keys for that bucket only. The write key may list and write but not delete, and goes into Render. The read key may list and read, and goes into the password manager and GitHub secrets for the restore test.
  5. Encryption key: Settings → Backups → Create encryption key shows it once. Save it in the password manager under two people, and keep a printed sealed copy in the office safe. Without this key the backups can't be read.
  6. Render → Environment: OFFSITE_ENDPOINT, OFFSITE_BUCKET, OFFSITE_KEY_ID, OFFSITE_SECRET, BACKUP_ENCRYPTION_KEY, BACKUP_HEARTBEAT_URL. Save, and the service restarts.
  7. Healthchecks.io check with a 1-hour period and a 2-hour grace period, alerting two people by email and SMS. Paste its URL into BACKUP_HEARTBEAT_URL.
  8. GitHub → Settings → Secrets → add the read key and the encryption key, then upload the workflow file. Run it once by hand: it should pass.
  9. Do the first hands-on restore drill and record it.
